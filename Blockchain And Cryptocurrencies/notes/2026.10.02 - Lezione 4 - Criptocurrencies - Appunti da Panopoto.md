# Modelli di Stato nelle Piattaforme Blockchain: UTXO vs Account-Based

Questo documento offre una trattazione teorico-architetturale completa e sistematica dei modelli di gestione dello stato nelle piattaforme crittografiche decentralizzate, basata sulla serie di slide del corso.

---

## 1. Tassonomia Generale delle Piattaforme Crypto

Nelle piattaforme blockchain, la rappresentazione e la persistenza dello stato globale si dividono fondamentalmente in due macro-paradigmi architetturali: **UTXO-based** e **Account-based** (quest'ultimo a sua volta declinato in **stateful** e **stateless**).

```
                            ┌────────────────────────┐
                            │    Crypto Platform     │
                            └───────────┬────────────┘
                                        │
              ┌─────────────────────────┴─────────────────────────┐
              ▼                                                   ▼
   ┌─────────────────────┐                             ┌─────────────────────┐
   │     UTXO-based      │                             │    account-based    │
   │    (es. Bitcoin)    │                             └──────────┬──────────┘
   └──────────┬──────────┘                                        │
              │                             ┌─────────────────────┴─────────────────────┐
              │                             ▼                                           ▼
              │                  ┌─────────────────────┐                     ┌─────────────────────┐
              │                  │      stateful       │                     │      stateless      │
              │                  │    (es. Ethereum)   │                     └─────────────────────┘
              │                  └─────────────────────┘
              ▼
   ┌─────────────────────┐
   │ Unspent Transaction │
   │    Output (UTXO)    │
   └─────────────────────┘
```

## 2. Il Paradigma UTXO-based (*Unspent Transaction Output*)

Nel paradigma **UTXO** (adottato originariamente da Bitcoin), il registro non memorizza "conti correnti" o saldi aggregati progressivi. Lo stato globale è costituito dall'insieme di tutte le quote di valore generate come output di transazioni passate e non ancora spese (**UTXO Set**).

### 2.1 Anatomia di un UTXO

```
┌───────────────────────────────────────────────┐
│                      tx1                      │
│                                               │
│       ┌───────────────────────────────┐       │
│       │             5:T→p1            │◄──────┼── Unspent Transaction Output (UTXO)
│       └───┬───────────────────────┬───┘       │
└───────────┼───────────────────────┼───────────┘
            │                       │
      ┌─────▼──────┐         ┌──────▼──────────────┐
      │   tokens   │         │ spending condition  │
      │   (5:T)    │         │      ("script")     │
      │            │         │        (→p1)        │
      └────────────┘         └─────────────────────┘
```

Ogni record generato all'interno di una transazione (`tx1`) è una coppia inscindibile composta da:

1. **Tokens (Valore/Asset):** la quantità economica associata (nell'esempio `5:T`, ovvero 5 unità del token $T$).
2. **Spending Condition ("Script"):** la condizione logica/crittografica vincolante richiesta per poter spendere quel valore (nell'esempio `→p1`, ovvero un predicato che richiede la firma crittografica corrispondente al titolare `p1`).

---

### 2.2 Principio Cardine: *Previous Checks* e Transizione di Stato

> **Regola Fondamentale Sottolineata dal Docente:**  
> *"In order to spend data/tokens, you have to do previous checks."*  
> Per spendere qualsiasi valore, non è possibile semplicemente dichiarare un trasferimento: una nuova transazione deve **fare riferimento esplicito a un output precedente**, verificare che sia ancora **non speso** (*unspent*) e **soddisfare la spending condition preesistente** (*script check*). Solo dopo il superamento dei controlli l'output precedente viene consumato.

```
┌───────────────────────────┐                 ┌───────────────────────────────────────────┐
│            tx1            │                 │                    tx2                    │
├───────────────────────────┤                 ├───────────────────────────────────────────┤
│                           │◄─── riferimento ┼─ (input consuma tx1 previa verifica)      │
│                           │     crittografico│                                           │
│       ┌───────────┐       │                 │       ┌───────────┐       ┌───────────┐   │
│       │  5:T→p1   │◄──────┼─────────────────┼───────┤   3:T→p2  │       │  2:T→p3   │   │
│       └───────────┘       │                 │       └───────────┘       └───────────┘   │
│        SPENT (●)          │                 │        UNSPENT (●)         UNSPENT (●)    │
└───────────────────────────┘                 └───────────────────────────────────────────┘
```

#### Meccanismo Operativo (Slide di Approfondimento):
1. **Verifica Preliminare (*Previous Check*):** Quando `tx2` intende spendere, punta all'output generato in `tx1` (`5:T→p1`). La rete verifica due condizioni:
   - **Validità dello stato:** Che `5:T→p1` sia attualmente **unspent** (verde), prevenendo il *double spending*.
   - **Soddisfacimento dello script:** Che la transazione `tx2` contenga i testimoni crittografici (firme/chiavi) che soddisfano la spending condition `p1`.
2. **Consumo Indivisibile (*Spent Output* - Rosso):** Una volta superato il controllo, l'output originario `5:T→p1` viene marcato come **speso** (*spent*, rosso). Esce definitivamente dall'insieme spendibile attivo della rete (*UTXO set*).
3. **Generazione di Nuovi Output (*Unspent Outputs* - Verdi):** Contestualmente, `tx2` genera due nuovi output spendibili:
   - `3:T→p2`: 3 token vincolati alla condizione di spesa di `p2`.
   - `2:T→p3`: 2 token vincolati alla condizione di spesa di `p3` (destinatario secondario o resto/*change* verso il mittente).
4. **Conservazione del Valore:** La somma degli output creati ($3 + 2 = 5$) deve corrispondere agli input consumati, al netto delle eventuali commissioni di rete (*miner fee*).

## 3. Il Paradigma Account-based

Nel modello **Account-based**, il "World State" è rappresentato come una grande tabella o mappa chiave-valore in cui ogni elemento è un **account** identificato da un indirizzo univoco (*address*).

### 3.1 Stateful vs Stateless

- **Stateful (es. Ethereum):** 
  Gli account conservano uno stato interno mutabile e persistente nel tempo (*contract storage*). L'esecuzione delle transazioni modifica deterministicamente sia i saldi dei wallet che i valori delle variabili interne registrate on-chain.
- **Stateless:** 
  Architetture in cui i nodi validatori non conservano permanentemente l'intero stato globale di tutti i contratti; le transazioni devono allegare una prova crittografica (es. *witness* / alberi crittografici) che certifichi la validità dello stato di partenza necessario per l'esecuzione.

---

### 3.2 Tipologie di Account nel Modello Stateful

```
                            ┌────────────────────────┐
                            │      Account-Based     │
                            └───────────┬────────────┘
                                        │
              ┌─────────────────────────┴─────────────────────────┐
              ▼                                                   ▼
┌─────────────────────────┐                               ┌─────────────────────────┐
│   User Accounts (EOAs)  │                               │    Contract Accounts    │
│   (Es. acct1, acct2)    │                               │  (Smart Contract acct3) │
└─────────────────────────┘                               └─────────────────────────┘
```

#### A. User Accounts / EOAs (*Externally Owned Accounts*)
- **Controllo:** Gestiti da entità esterne alla rete mediante una coppia di chiavi asimmetriche (pubblica/privata).
- **Iniziativa:** Hanno la facoltà esclusiva di firmare e iniziare attivamente una transazione, pagando le commissioni di calcolo (*gas fee*).
- **Struttura (da slide):**
  - **`acct1`:** stato interno `x=1, y=7` | wallet: `5:T`
  - **`acct2`:** stato interno `x=2, b=false` | wallet multi-asset: `1:T, 3:T'`

#### B. Stateful Contract Accounts (*Smart Contracts*)
Come sottolineato nelle lezioni:
> *"Contract accounts can have **code**, **state**, and **tokens**."*

```
┌───────────────────────────────────────────────┐
│                     acct3                     │
├───────────────────────────────────────────────┤
│  state: z=1                                   │ ◄── Stato interno (Storage)
│  wallet: 10:T                                 │ ◄── Saldo autonomo di token
│  code:                                        │ ◄── Logica procedurale immutabile
│    pay(b,x) {                                 │
│      if z==0 then abort else                  │
│      transfer x:T from acct3 to b             │
│    }                                          │
│    lock() {                                   │
│      if signedBy(alice) z=0                   │
│    }                                          │
└───────────────────────────────────────────────┘
```

- **Code:** Codice immutabile che stabilisce i vincoli di esecuzione (es. `pay` abortisce se $z=0$; `lock` imposta $z=0$ solo se firmato da Alice).
- **State:** Variabili on-chain persistenti soggette a mutazione (es. flag $z=1$).
- **Wallet / Tokens:** Disponibilità patrimoniale detenuta in modo autonomo dal contratto stesso ($10:T$).
- **Esecuzione reattiva:** Un contratto non agisce mai autonomamente; si attiva solo in risposta a una transazione in ingresso ricevuta da un EOA o da un altro contratto.

## 4. Transizione di Stato nel Modello Account-based

Mentre nel modello UTXO gli elementi di stato vengono consumati (diventano *spent*) e ricreati (*unspent*), nel modello account-based la transizione è un **aggiornamento algebrico in-place** dello stato globale.

### Esempio della Transazione (Slide 26)

$$\texttt{acct3.pay(acct1, acct2, 1)}$$

```
     STATO INIZIALE (S)                                          STATO FINALE (S')
┌───────────────────────────┐                               ┌───────────────────────────┐
│           acct1           │                               │           acct1           │
│ state: x=1, y=7           │                               │ state: x=1, y=7           │
│ wallet: 5:T               │                               │ wallet: 4:T  ◄── (-1:T)   │
└───────────────────────────┘       TRANSAZIONE DIRETTA     └───────────────────────────┘
                                  acct3.pay(acct1,acct2,1)
┌───────────────────────────┐    ────────────────────────►  ┌───────────────────────────┐
│           acct2           │                               │           acct2           │
│ state: x=2, b=false       │                               │ state: x=2, b=false       │
│ wallet: 1:T, 3:T'         │                               │ wallet: 2:T, 3:T' ◄── (+1)│
└───────────────────────────┘                               └───────────────────────────┘

┌───────────────────────────┐                               ┌───────────────────────────┐
│           acct3           │                               │           acct3           │
│ pay(a,b,x) {              │                               │ pay(a,b,x) {              │
│   transfer x:T from a to b│                               │   transfer x:T from a to b│
│ }                         │                               │ }                         │
└───────────────────────────┘                               └───────────────────────────┘
```

- **Bilanci:** `acct1` passa da $5$ a **$4:T$**; `acct2` passa da $1$ a **$2:T$** (con il token secondario $3:T'$ invariato).
- **Stato interno:** Le variabili interne non coinvolte (`x, y` e `x, b`) rimangono inalterate.
- **Nessuna creazione/distruzione di conti:** Gli account preesistono e continuano a esistere dopo il trasferimento con i registri aggiornati.

## 5. Sintesi Comparativa dei Due Paradigmi

| Caratteristica | Modello UTXO-based | Modello Account-based |
| :--- | :--- | :--- |
| **Elemento atomico** | Singolo output non speso (`tokens` + `spending condition`) | Singolo conto identificato da un `address` (`wallet` + `state` + `code`) |
| **Requisito di spesa (*Spend requirement*)** | **Previous Checks**: Verifica che l'output referenziato sia *unspent* e soddisfacimento dello script | Firma di autorizzazione transazionale inviata da un account abilitato con saldo sufficiente |
| **Meccanismo di transazione** | Consuma completamente gli UTXO in input (spent) e ne crea di nuovi in output (unspent) | Modifica incrementale/decrementale dei registri di saldo esistenti |
| **Calcolo del saldo** | Somma aggregata di tutti gli UTXO spendibili appartenenti a una chiave | Saldo esplicito memorizzato direttamente nel record dell'account |
| **Concorrenza e Parallelismo** | Elevata: transazioni che usano UTXO disgiunti possono essere eseguite in parallelo | Più complessa: transazioni sullo stesso conto introducono dipendenze di lettura/scrittura |
| **Smart Contract** | Script di validazione associati a singole monete (generalmente non Turing-completi) | Programmi Turing-completi che mantengono memoria di stato condivisa (*stateful*) |
| **Piattaforme di riferimento** | Bitcoin, Cardano | Ethereum, Avalanche, Solana |
