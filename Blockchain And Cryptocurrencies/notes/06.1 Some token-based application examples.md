Breve panoramica sugli usi pratici dei token visti nel Cap. 5: come si raccolgono fondi emettendo token (ICO e successori) e come i token diventano strumento di governance (DAO, con Dash come caso reale). Subito dopo la lezione passa al set di slide su Ethereum.

---

## 1. Fondamenti

### 1.1 ICO — Initial Coin Offering

Una ICO è un modo **non regolamentato** di raccogliere fondi per un progetto emettendo token: i sostenitori pagano in (cripto)valuta e ricevono token, con la logica *"se riceviamo i fondi, portiamo avanti il progetto"*. Viene spesso chiamata **crowdsale**.

La differenza con il crowdfunding classico è che lì si **dona** a una causa, mentre nella ICO si **investe**: se il progetto cresce, cresce anche il valore dei token. Ethereum è stata la piattaforma più usata per lanciarle (token ERC-20).

Molto popolari in passato, hanno perso credibilità per l'enorme quantità di **scam**: molti progetti esistevano solo per incassare e sparire. Da qui le evoluzioni successive.

### 1.2 Token e governance

Oltre a rappresentare un investimento, un token può dare **diritti di voto**. È il presupposto delle DAO: chi detiene token partecipa alle decisioni dell'organizzazione.

---

## 2. Architettura

### 2.1 Evoluzione dei metodi di raccolta fondi

**ICO → STO → IEO → IDO**: ogni passo cerca di ridurre il rischio di frode aggiungendo una garanzia.

| Metodo | Cosa aggiunge |
|---|---|
| **ICO** | Solo un'idea/promessa, nessun collaterale |
| **STO** — Security Token Offering | Il token rappresenta una **security**, cioè un investimento garantito da un asset reale (*backed by asset*). La proprietà è registrata on-chain e l'offerta rispetta la **normativa**. Approccio ibrido tra ICO e IPO tradizionale |
| **IEO** — Initial Exchange Offering | Un **exchange centralizzato** fa da intermediario: il team crea i token e promuove il progetto, l'exchange li lista e gestisce la distribuzione. L'exchange "ci mette la faccia" → più fiducia |
| **IDO** — Initial DEX Offering | Come la IEO ma su un **exchange decentralizzato (DEX)**, cioè basato su smart contract; spesso i token finiscono subito in una **liquidity pool** |

A livello normativo, i vari Stati si sono mossi in modo diverso: alcuni hanno introdotto regole, altri hanno semplicemente vietato questi strumenti.

### 2.2 DAO — Decentralized Autonomous Organization

Una DAO è un'organizzazione tradizionale ma **decentralizzata**, le cui regole vivono in smart contract. Il contratto può contenere:

- il registro delle quote (holdings) di ciascun membro;
- un sistema di voto per scegliere board e "dipendenti";
- la gestione di beni e fondi (*smart property management*).

Caratteristiche: presenza di un **token** interno, **autonomia** (una volta deployata è indipendente dai creatori, codice open source) e **consenso** dei membri sulle decisioni.

Come funziona:

- **Proposals**: sono il modo principale di prendere decisioni. Per evitare spam, la DAO può richiedere un **deposito** per presentarle.
- **Voting**: dopo la presentazione, i token holder votano.
- **Contractors**: una DAO non può scrivere codice o costruire prodotti da sola; affida il lavoro a **contractor** scelti con il voto.

**TheDAO (2016)** è il primo caso famoso, su Ethereum. Ebbe gravi problemi: una vulnerabilità di **reentrancy** permise di drenare circa un terzo dei fondi raccolti, e la reazione della community portò all'hard fork che separò **Ethereum** da **Ethereum Classic**.

### 2.3 Dash — una DAO "in produzione"

Dash è una criptovaluta nata da Bitcoin (fork del codice, PoW) che integra la governance direttamente nel protocollo, dividendo il block reward invece di darlo tutto ai miner:

| Destinatario | Quota (slide) | Ruolo |
|---|---|---|
| **Miners** | 45% | Producono i blocchi (PoW), come in Bitcoin |
| **Masternodes** | 45% | Nodi che bloccano un collaterale in DASH; offrono servizi extra e **votano** le proposte |
| **Treasury** | 10% | Budget accantonato e assegnato ai **contractor** in base alle **proposal** approvate dai masternode |

È la stessa logica *proposal → voto → contractor* delle DAO, ma finanziata dal block reward.

## 3. Trade-off e attacchi

| Rischio / limite | Perché | Mitigazione |
|---|---|---|
| Scam nelle ICO | Nessun collaterale né regolamentazione: basta una promessa | STO (asset + regole), IEO (exchange garante) |
| Rischio di controparte nelle IEO | Si torna a fidarsi di un intermediario centralizzato | IDO su DEX e smart contract |
| Bug nel codice della DAO | Il contratto è autonomo e immutabile: un bug diventa una regola | Audit, pattern sicuri (checks-effects-interactions), in extremis hard fork (TheDAO) |
| Spam di proposal | Proporre è gratuito | Deposito obbligatorio per proporre |
| Concentrazione del voto | Il peso dipende dai token posseduti | Soglie di quorum, collaterale alto (masternode Dash) |

## 4. Esempi e codice

### 4.1 Proposal e voto in una DAO (schema minimo)

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

interface IERC20 { function balanceOf(address) external view returns (uint256); }

contract MiniDAO {
    IERC20 public token;              // token di governance
    uint256 public constant DEPOSIT = 0.1 ether; // anti-spam

    struct Proposal { address contractor; uint256 amount; uint256 yes; uint256 no; bool done; }
    Proposal[] public proposals;
    mapping(uint256 => mapping(address => bool)) public voted;

    constructor(IERC20 _token) { token = _token; }

    function propose(address contractor, uint256 amount) external payable {
        require(msg.value == DEPOSIT, "deposito richiesto");
        proposals.push(Proposal(contractor, amount, 0, 0, false));
    }

    function vote(uint256 id, bool support) external {
        require(!voted[id][msg.sender], "gia votato");
        uint256 weight = token.balanceOf(msg.sender); // voto pesato sui token
        voted[id][msg.sender] = true;
        if (support) proposals[id].yes += weight; else proposals[id].no += weight;
    }

    function execute(uint256 id) external {
        Proposal storage p = proposals[id];
        require(!p.done && p.yes > p.no, "non approvata");
        p.done = true;                               // effetto PRIMA dell'interazione
        payable(p.contractor).transfer(p.amount);    // paga il contractor dalla treasury
    }

    receive() external payable {} // la DAO riceve fondi (treasury)
}
```

> Semplificato: manca una scadenza del voto e il voto pesato su `balanceOf` è vulnerabile al riuso degli stessi token da indirizzi diversi (nelle DAO reali si usano snapshot).

### 4.2 Il bug di TheDAO (reentrancy)

```solidity
// VULNERABILE: invia ETH prima di azzerare il saldo
function withdraw() external {
    uint256 amount = balances[msg.sender];
    (bool ok, ) = msg.sender.call{value: amount}(""); // il chiamante può rientrare qui
    require(ok);
    balances[msg.sender] = 0;                          // troppo tardi
}
```

Il contratto chiamante, nella sua `receive()`, richiama `withdraw()` prima che il saldo venga azzerato e preleva più volte. La correzione è aggiornare lo stato **prima** della chiamata esterna (checks-effects-interactions).

## 5. Quadro di riepilogo

> 💡 **Punti su cui insiste il Prof.** Panoramica veloce: conta capire l'**evoluzione ICO → IDO** (ogni passo aggiunge una garanzia) e lo schema **proposal → voto → contractor** delle DAO, con Dash come esempio del block reward diviso tra miner, masternode e treasury.

### 5.1 Concetti chiave

| Concetto | In sintesi |
|---|---|
| ICO / crowdsale | Raccolta fondi non regolamentata in cambio di token; molti scam |
| STO | Token come security, garantito da asset reali e regolamentato |
| IEO | Offerta gestita da un exchange centralizzato che fa da garante |
| IDO | Offerta su DEX tramite smart contract e liquidity pool |
| DAO | Organizzazione governata da smart contract e voto dei token holder |
| TheDAO | Prima DAO famosa (2016), hack per reentrancy → fork ETH/ETC |
| Dash | Block reward diviso: miners, masternodes (votano), treasury (finanzia proposal) |
